# Сайт Ники Дупиной

Лендинг, личный кабинет клиента и админка. Фронт — статичные страницы без сборщика, бэкенд — папка `server/`.

## Запуск на своём компьютере

Нужен только [Docker Desktop](https://www.docker.com/products/docker-desktop/) (запущенный).

```
./start.sh
```

Первый запуск занимает пару минут. Скрипт сам создаст файл `.env` с локальными настройками, поднимет базу, хранилище видео и почту, загрузит демо-данные.

| Что | Адрес |
|---|---|
| Сайт, ЛК, админка | http://localhost:3000 |
| Письма с кодами входа | http://localhost:8025 |

Остановить: `docker compose down`. Стереть все локальные данные и начать заново: `docker compose down -v`.

### Демо-данные
- Админы: nika@example.com (видит всё), diana@example.com, karolina@example.com (тех. доступ).
- Клиенты: 6 человек с разными тарифами: 1 доступ действует, 3 заканчиваются в ближайшие 7 дней, 2 закончились.
- 3 оплаты, 5 демо-видео, 11 товаров с ценами лендинга, 2 заявки.

## Как устроено

```
браузер ──► nginx (на бою) ──► статика сайта (html, css, js)
                         └──► /api/*  ──► server (Node.js + Fastify) ──► PostgreSQL
браузер ──► подписанная ссылка ──► S3 (видео, напрямую, минуя сервер)
```

Локально nginx нет: статику и `/api` раздаёт сам сервер на порту 3000.

```
server/
  src/          код сервера (config.js читает все настройки из переменных окружения)
  migrations/   изменения базы по порядку (001_init.sql — все таблицы)
  scripts/      setup.js: миграции → хранилище → демо-данные (не на бою)
  seed/         демо-данные и 5 коротких демо-видео
  s3/cors.xml   CORS для боевого бакета
  test/         автотесты
.env.example    список всех настроек без значений
```

## Переход на боевой сервер

Код не меняется, меняются только значения в `.env` на сервере (имена из `.env.example`): адрес сайта, база, S3 Timeweb, почтовый сервис, ключи Robokassa, секрет сессий. `NODE_ENV=production` включает строгие проверки: адрес только https, секрет не короче 64 символов, демо-данные не загружаются.

### CORS боевого бакета
При каждой выкладке `server/scripts/setup.js` сам ставит CORS на бакет с видео (только `PUBLIC_URL`, `ExposeHeaders ETag`), руками ничего делать не нужно. Принял ли Timeweb это правило, проверяется после первой выкладки: в панели бакет → «Настройки» → CORS. `ExposeHeaders ETag` обязателен: без него загрузка видео частями из браузера не работает. Файл `server/s3/cors.xml` остаётся запасным вариантом: если Timeweb не примет правило через API, его вставляют в тот же пункт панели вручную, заменив `https://example.ru` на домен сайта.

## Вход (фаза 1)

| Адрес | Что делает |
|---|---|
| `POST /api/auth/code` | письмо с кодом (и ссылкой для клиента). Ответ всегда одинаковый |
| `POST /api/auth/verify` | код → сессия. 10 минут, одноразовый, 5 попыток |
| `POST /api/auth/link` | ссылка из письма → сессия. 15 минут, одноразовая; `check: true` только проверяет |
| `POST /api/auth/password` | вход паролем. Ошибка всегда «неверная почта или пароль» |
| `POST /api/auth/logout` | выход, сессия удаляется на сервере |
| `GET /api/me`, `PUT/DELETE /api/me/password` | профиль клиента, задать или убрать пароль |
| `GET /api/admin/me` | профиль админа. Все `/api/admin/*` проверяют вход админа на сервере |

Лимиты: 3 письма на почту за 15 минут и 10 за сутки; 10 запросов кода с одного адреса за 15 минут; 5 неверных паролей на почту за 15 минут.
Сессии: кука HttpOnly, SameSite=Lax (на https ещё Secure и префикс `__Host-`). С галочкой «запомнить»: кабинет 30 дней с продлением при заходе, админка 14 дней. Без галочки до закрытия браузера (на сервере не дольше 12 часов без действий).
Все изменяющие запросы принимаются только со своего сайта и только в формате JSON (защита от подделки запросов).

## Клиенты, тарифы, доступ (фаза 2)

Срок доступа хранится в днях: недели × 7, «24 часа» = 1 день. Продление считается от текущей даты окончания, если доступ идёт, иначе от сегодняшнего момента. Каждое продление — отдельная строка в `access_periods` (видно, кто и когда добавил). Закрытие вручную ставит `closed_at`, открыть снова можно в любой момент (срок тогда от сегодня).
Метка: зелёная, жёлтая («осталось 7 дней и меньше»), красная (закончился или закрыт), «нет доступа» (ещё не открывали). Доступ на 24 часа жёлтым не бывает.

| Адрес | Роли | Что делает |
|---|---|---|
| `GET /api/admin/clients`, `GET /api/admin/clients/:id` | все админы | список с метками; карточка с оплатами и историей |
| `POST /api/admin/clients`, `PATCH /api/admin/clients/:id` | все админы | добавить клиента; имя, почта, телефон, заметка. Смена почты закрывает сессии клиента |
| `POST /api/admin/clients/:id/access` | все админы | `{ days, tariffId, note }` — открыть или продлить |
| `POST /api/admin/clients/:id/access/undo` | все админы | отменить своё последнее продление (до 15 минут, только ручное) |
| `POST /api/admin/clients/:id/access/close` | все админы | закрыть доступ, `{ note }` |
| `POST /api/admin/clients/:id/remind` | все админы | отметка «написали о продлении» |
| `GET /api/admin/purchases` | все админы | последние оплаты для экрана «Сегодня» |
| `GET /api/admin/tariffs`, `PATCH /api/admin/tariffs/:id` | owner, tech | цены в рублях, `{ price, old }` |
| `GET /api/admin/log` | owner, tech | журнал действий (входы не показываем, в базе они есть) |
| `GET /api/me/access` | клиент | «Мой доступ»: метка, срок, тариф, оплаты |
| `GET /api/tariffs` | публичный | цены и названия с сервера |

Роли: owner (Ника) и tech (Каролина) — всё; staff (Диана) — клиенты и доступ, без цен и журнала. Проверка на сервере в каждом маршруте.
Видео, материалы и заявки в админке пока демо (фазы 3 и 5).

## Оплата (фаза 4)

Robokassa + «Робочеки СМЗ». Цена берётся только из базы по артикулу товара, доступ открывает только уведомление Robokassa с верной подписью.

Путь покупателя: `checkout.html` → сервер создаёт заказ (`POST /api/pay/start`) и отдаёт ссылку → страница оплаты Robokassa (карта, СБП) → `spasibo.html?t=pay` спрашивает статус заказа, пока сервер не получит уведомление (до минуты, потом текст «оплата обрабатывается»).

### Что вписать в кабинете Robokassa (Настройки магазина → Технические настройки)
- Алгоритм подписи: **MD5**.
- Result URL: `https://<домен>/api/pay/result`, метод **POST**.
- Success URL: `https://<домен>/spasibo.html?t=pay`, метод **GET**.
- Fail URL: `https://<домен>/spasibo.html?t=fail`, метод **GET**.
- Пароли #1 и #2 (боевые и отдельно тестовые) → в `.env` сервера: `ROBOKASSA_LOGIN`, `ROBOKASSA_PASSWORD1`, `ROBOKASSA_PASSWORD2`. `ROBOKASSA_TEST=1` — тестовые платежи, `0` — боевые. В репозиторий пароли не попадают.
- В «Мой налог» → Партнёры разрешить доступ Robokassa (Робочеки СМЗ).

### Чек
В каждый платёж передаётся `Receipt`: одна позиция, название товара (до 128 символов), `quantity 1`, `payment_method full_payment`, `payment_object service`, `tax none`. Без него Робочеки СМЗ чек не формируют. Название в чеке = название тарифа в базе, поэтому названия тарифов полные («Тренировки онлайн, 1 месяц»).

### Возвраты и сбои
Админка → Ещё → Оплаты. «Оплата пришла» — если деньги видны в кабинете Robokassa, а уведомление не дошло. «Оформить возврат» — после возврата денег в кабинете Robokassa: закрывает доступ этого заказа (последующие продления сдвигаются назад) или убирает купленный материал. Заметка обязательна, всё пишется в журнал. Все уведомления Robokassa, включая отклонённые, лежат в таблице `payment_events` (без почты и данных карты).

## Выкладка на боевой сервер (фаза 6)

Подготовлено, но выключено: пока в настройках репозитория нет переменной `DEPLOY_ENABLED = true`, ничего не выкладывается.

```
GitHub (пуш в main) ──► Проверки: автотесты, уязвимости, скрипты, nginx
                    └─► Выкладка: код по SSH-ключу → .env из секретов → remote-deploy.sh
VPS: nginx (HTTPS, заголовки, CSP, лимит запросов) ──► статика /srv/nika/current/public
                                                  └──► /api → приложение (Docker, 127.0.0.1:3000) → PostgreSQL (Docker, 127.0.0.1)
Ночью: бэкап базы → шифрование → отдельный S3. По воскресеньям: пробное восстановление.
```

| Файл | Что делает |
|---|---|
| `.github/workflows/ci.yml` | тесты на каждый пуш, `npm audit`, проверка скриптов и конфига nginx |
| `.github/workflows/deploy.yml` | выкладка на пуш в `main` или кнопкой Run workflow |
| `deploy/cloud-init.yaml` | вставить при создании сервера, заменив домен, почту и публичный ключ |
| `deploy/server/setup.sh` | первичная настройка сервера (запускает cloud-init) |
| `deploy/server/remote-deploy.sh` | образ, миграции, заголовки, переключение, проверка `/api/health`, откат при сбое |
| `deploy/server/backup.sh`, `restore-test.sh` | бэкап и пробное восстановление; при сбое письмо на `ALERT_EMAIL` |
| `deploy/compose.prod.yml`, `deploy/Dockerfile` | база и приложение на сервере |
| `deploy/nginx/nika.conf` | HTTPS, кэш, закрытые служебные файлы, лимит запросов к API |

### Что настраивает сервер
HTTPS Let's Encrypt с автопродлением; открыты только порты 22, 80, 443; вход по SSH только по ключу и только пользователю `deploy`, root закрыт; fail2ban; автообновления безопасности с перезагрузкой в 04:30 по Хабаровску; база и приложение слушают только 127.0.0.1; подкачка 2 ГБ; логи с ротацией.

### Секреты и переменные GitHub
Где: репозиторий → Settings → Environments → `production` (создать) → Environment secrets / Environment variables. Переменная `DEPLOY_ENABLED` — там же или в Settings → Secrets and variables → Actions → Variables.

**Секреты (скрытые):** `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`, `SESSION_SECRET`, `DB_PASSWORD`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `SMTP_USER`, `SMTP_PASSWORD`, `ROBOKASSA_LOGIN`, `ROBOKASSA_PASSWORD1`, `ROBOKASSA_PASSWORD2`, `BACKUP_S3_ACCESS_KEY`, `BACKUP_S3_SECRET_KEY`, `BACKUP_PASSPHRASE`.

**Переменные (видимые):** `DEPLOY_ENABLED`, `SSH_HOST`, `PUBLIC_URL`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `MAIL_FROM`, `MAIL_REPLY_TO`, `ADMIN_NOTIFY_EMAIL`, `ROBOKASSA_TEST`, `INITIAL_ADMINS`, `BACKUP_S3_ENDPOINT`, `BACKUP_S3_REGION`, `BACKUP_S3_BUCKET`, `ALERT_EMAIL`.

### Первый запуск на бою
Демо-данных нет. Один раз загружается каталог товаров (`server/seed/catalog.sql`) и админы из `INITIAL_ADMINS`. Без владельца (owner) сервер не стартует.

### Мониторинг
`https://<домен>/api/health` отвечает 200, если база и хранилище работают, иначе 503. Его подключают к внешнему сервису проверки доступности.
